# Scope Creep Guard — веб-MVP (продукт 2)

Спецификация для начальной реализации. Язык интерфейса — **английский**.

Дизайн-референс — **Fenscope** (fenscope.com): тёмная тема (базовый фон около `#0e0d0c`), однаколоночный лендинг, инструмент как продолжение страницы. Берём структуру блоков, плотность и тон — не копипастим тексты и не тянем их картинки.

---

## 1. Что это

Инструмент, который помогает фрилансерам отбиваться от бесплатных доделок.

Пользователь вставляет условия проекта (договор или принятое ТЗ), затем вставляет входящее сообщение клиента вида «а можешь ещё быстренько...». Получает вердикт: входит запрос в договорённости или нет, почему, плюс готовый вежливый ответ клиенту, который можно скопировать и отправить.

**Это тест спроса, а не продукт.** Механика ровно одна. Ничего сверх описанного ниже не добавлять.

---

## 2. Стек и ограничения

- Node.js + Express (или Fastify), Postgres, серверный рендер или простой SPA — на усмотрение, но без тяжёлых фреймворков
- Деплой на VPS (Ubuntu, Финляндия), домен-поддомен `scopeguard.*`
- Один внешний вызов — LLM API

**Чего не делать:**

- Регистрации, паролей, входа, личного кабинета, истории вердиктов
- Загрузки файлов — только вставка текста
- Биллинга — кнопка на экране цены никуда не ведёт
- Change Order в PDF — только текстом на экране

---

## 3. Воронка

```
лендинг → экран 1 (условия) → экран 2 (запрос клиента) → email-гейт → вердикт → экран цены
```

Email спрашивается **до показа вердикта**, не после. Это принципиально: почта, отданная за уже полученную пользу, не измеряет то, что мы измеряем.

Две целевые метрики:

1. `email_submit` — оставил почту (в отчёте: «регистрация»)
2. `verdict_shown` — увидел вердикт (в отчёте: «активация»)

---

## 4. Бизнес-логика вердикта

### 4.1 Что на входе

Два текстовых поля:

- **`scope`** — условия проекта. Договор, SOW, принятое ТЗ, переписка с договорённостями. Ограничение 200–15000 символов.
- **`request`** — входящее сообщение клиента. 20–3000 символов.

Валидация только по длине и на непустоту. Не пытаться определять «похоже ли это на договор» — оставим живым людям.

### 4.2 Что на выходе

Строгий JSON:

```json
{
  "verdict": "in_scope" | "out_of_scope" | "unclear",
  "confidence": "high" | "medium" | "low",
  "reasoning": "1–2 предложения со ссылкой на конкретное место в условиях",
  "evidence": "точная цитата из scope, на которую опирается вердикт, или null",
  "reply": "готовый текст ответа клиенту, 3–6 предложений",
  "change_order": {
    "summary": "формулировка доработок одной строкой",
    "suggested_terms": "что уточнить: объём, срок, оплата"
  } | null
}
```

`change_order` заполняется только при `out_of_scope`. При `unclear` — null, но `reply` в этом случае просит клиента уточнить, а не выставляет счёт.

### 4.3 Правила для модели

Закладываются в системный промпт, каждое существует из-за конкретного риска:

1. **Опираться только на текст условий.** Не достраивать «обычно в такие проекты входит...». Если в условиях этого нет — это `unclear`, а не `out_of_scope`.
2. **Считать не только тему, но и количество.** Если условия ограничивают число правок, итераций, страниц — исчерпанный лимит делает запрос `out_of_scope`, даже когда сама тема входит.
3. **Не отказывать по инерции.** Запрос, прямо покрытый условиями, — `in_scope`, точка. Инструмент, который на всё отвечает «это вне рамок», вреден: фрилансер один раз отправит такой ответ и потеряет клиента.
4. **`unclear` — полноценный вердикт, а не отказ.** При расплывчатых условиях честно указать, что формулировка допускает разночтения, и предложить что уточнить.
5. **`evidence` — дословная цитата** из `scope`, не пересказ. Если процитировать нечего, вердикт не может быть `high` confidence.
6. **Тон `reply`**: дружелюбный, деловой, без извинений за постановку вопроса и без обвинений. Не «I apologize for any inconvenience», не «this was never part of our agreement». Формула: признать запрос → назвать статус → предложить путь дальше.
7. **Язык `reply`** — язык сообщения клиента. Условия могут быть на другом языке, ответ пишется на языке `request`.
8. **Никаких сумм.** Модель не придумывает цены и часы — в `suggested_terms` только указание, что это нужно определить.

### 4.4 Обработка вызова

- Таймаут 30 секунд, один автоматический ретрай
- Ответ парсится как JSON; при невалидном — один повтор с уточнением формата, дальше показать ошибку и предложить повторить
- Логировать: длины входов, вердикт, confidence, время ответа, стоимость. **Тексты пользователей не логировать** — мы обещаем на лендинге, что не храним их (см. 7)
- Потолок трат на ключе выставить до запуска рекламы

### 4.5 Лимит

Одна проверка на посетителя, ограничение по связке email + cookie. Вторая попытка показывает экран цены с текстом, что дальнейшие проверки — в платной версии.

Лимит не пытаться сделать неломаемым: обход через инкогнито возможен, и это нормально. Задача — не защитить выручку, а не дать выжечь бюджет на API.

## 5. Экраны

### 5.1 Лендинг

Структура (порядок по Fenscope):

1. **Hero** — заголовок про бесплатные доделки, подзаголовок с цифрой потерь, кнопка `Check a client request`
2. **Как это работает** — три шага: вставь условия → вставь сообщение клиента → получи вердикт и готовый ответ
3. **Пример вердикта** — статичный, реальный, с подсветкой цитаты из условий. Показывает результат до того, как человек что-то ввёл
4. **Что это ловит** — доделки под видом мелочи, лишние раунды правок, размытые формулировки
5. **Конфиденциальность** — отдельным блоком, см. 7
6. **Финальный CTA**
7. **Футер** — privacy, terms

### 5.2 Экран 1 — условия проекта

Большое текстовое поле, заголовок `Paste what you agreed to`, подсказка про договор / SOW / принятое предложение.

Кнопка `Use an example` подставляет готовый образец договора — для тех, у кого договора нет под рукой. Без неё потеряем часть людей прямо здесь.

### 5.3 Экран 2 — запрос клиента

Поле поменьше, заголовок `Paste the client's message`. Условия сверху показаны свёрнутым блоком с возможностью развернуть и поправить.

Кнопка `Check this request`.

### 5.4 Email-гейт

Открывается по клику на `Check this request`. Одно поле — email.

Текст: результат придёт на экран сразу, почта нужна, чтобы прислать доступ, когда откроем полную версию. Не врать про «отправим отчёт на почту», если не отправляем.

Валидация формата, блок одноразовых доменов. После успешной отправки — сразу запуск проверки, без лишнего клика.

### 5.5 Ожидание

Проверка занимает 5–15 секунд. Пустой спиннер на такое время читается как зависание — показывать смену подписей по шагам («reading your agreement» → «comparing the request» → «drafting your reply»).

### 5.6 Вердикт

Главный экран, ради него всё.

- **Крупный статус**: `In scope` / `Out of scope` / `Unclear`, цветом
- **`reasoning`** под ним
- **`evidence`** — цитата из условий, визуально как цитата
- **`reply`** — в блоке с кнопкой `Copy reply`. Это то, ради чего человек пришёл, блок должен быть самым заметным после статуса
- **`change_order`** — ниже, сворачиваемый
- При `low` confidence — явная пометка, что условия допускают разночтения

### 5.7 Экран цены

Показывается под вердиктом, после того как человек его увидел.

`$19/month`, ниже — что входит (безлимит проверок, история, несколько проектов). Кнопка `Get early access`, ничего не делающая, кроме события. Рядом нейтральный выход `Not now` — тоже с событием, чтобы в отчёте отличать отказ от игнора.

Цена — предмет согласования с заказчиком, в коде вынести в конфиг.

## 6. Аналитика

GA4, все события с `product: "scopeguard"`.

**Целевые:**

| Событие | Когда |
|---|---|
| `email_submit` | Успешно принята почта |
| `verdict_shown` | Вердикт отрисован на экране |

**Вспомогательные:**

| Событие | Когда |
|---|---|
| `cta_click` | Клик по кнопке с лендинга |
| `scope_filled` | Переход с экрана 1 на экран 2 |
| `example_used` | Использован образец договора |
| `verdict_result` | Вместе с вердиктом, параметры: verdict, confidence |
| `reply_copied` | Копирование ответа |
| `change_order_open` | Раскрытие блока |
| `price_screen_view` / `price_cta_click` / `price_dismiss` | Экран цены |
| `verdict_error` | Ошибка вызова модели |

`email_submit` и `verdict_shown` импортируются в Google Ads как конверсии.

`reply_copied` формально не в KPI, но это единственная метрика реальной пользы — в отчёте она будет самой содержательной.

`gclid` и utm читаются из URL при входе, кладутся в `sessionStorage` и уходят вместе с почтой.

## 7. Конфиденциальность

Люди вставляют договоры с клиентами. Без явных гарантий часть аудитории отвалится на первом экране, и мы получим заниженный CR не из-за отсутствия спроса.

- Отдельный блок на лендинге и строка над полем ввода: тексты не сохраняются, используются только для этой проверки
- **И это должно быть правдой**: в базу пишем только email, метки, вердикт, confidence, timestamp, длины входов. Сами тексты — никуда, включая логи
- `privacy.html` и `terms.html` обязательны для модерации Google Ads. Делать заранее, не в день запуска
- Cookie-баннер для UK

## 8. База

Одна таблица:

```
leads_scopeguard
  id, email, created_at,
  gclid, utm_source, utm_medium, utm_campaign, utm_term,
  verdict, confidence, scope_len, request_len,
  reply_copied (bool), price_cta (bool)
```

Ежедневный дамп по крону. Потеряем данные на третьей неделе — потеряем тест.

## 9. Порядок работ

1. Промпт и схема ответа — прогнать вручную на 5 кейсах до всякого кода
2. Бэкенд: эндпоинт проверки, вызов модели, валидация, лимит
3. Экраны 1–2, email-гейт, экран вердикта
4. Лендинг
5. Аналитика
6. privacy / terms / cookie-баннер
7. Прогон 15–20 кейсов, правка промпта

Если сроки поедут — первым режется `change_order`, вторым экран цены. Вердикт и `reply` не режутся никогда: без них измерять нечего.
